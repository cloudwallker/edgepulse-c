## 本轮 ACK 可靠传输

默认不启用 ACK；`--reliable` 增加停等式可靠发送，可与原来的 `--seed`、`--ticks`、`--json` 和 `--store` 组合。该模式不会改变配置文件格式或配置命令去重语义。

每个队首最多调用 4 次发送 HAL，包含首次和最多 3 次重传，相邻尝试至少间隔 100 ms。返回 `false` 的调用也消耗预算并进入同样的退避；第 4 次调用后再等待 100 ms，仍未确认则增加 `delivery_timeouts` 并丢弃该队首，当前 tick 不发送下一帧。每次 tick 最多一次 HAL 调用，重传使用同一设备、启动、序号和负载。看门狗优先处理长停顿，清空队列与在途状态，但保留可靠模式。

ACK 为类型 3、负载长度 0，设备/启动/序号必须精确匹配当前队首，而且该队首至少有一次 HAL 调用返回成功。后续重传失败不会抹去先前成功提交的 ACK 资格。重复 ACK、旧会话 ACK、已超时帧 ACK 或其他不匹配 ACK 均不出队。调用串行且不可重入：模拟器先缓存 ACK，在 `ep_device_tick` 及发送回调返回后才派发。

接收模块使用显式的设备/启动会话，由可信控制调用 `ep_receiver_begin_session` 切换；普通收到的数据不能触发会话切换。窗口缓存最近 16 个完整已接受帧；有效遥测要求类型 1、长度 9、告警为 0/1，并匹配会话。相同缓存帧重发只增加重复指标并再次 ACK，不重复交付；相同缓存序号、不同负载返回冲突且不 ACK。

缓存外的新序号按无符号序号距离判断，仅接受 `0 < distance < 2^31`，允许跳号和 uint32 回绕。缓存已淘汰的旧帧、乱序、相等及恰好半圈歧义均拒绝，首个有效帧则建立会话高水位。应用交付回调成功后才更新缓存/高水位并写 ACK；失败只增加失败指标，原缓存、高水位与 ACK 输出保留，后续可重试。回调返回成功表示应用接受，不表示持久化；如果先产生副作用再返回失败，重试可能重复该副作用。

主机模拟通过两个独立的真实 CRC 解析器传输遥测与 ACK 字节，随机分片并在明确的模拟包空闲边界 flush。固定种子控制可重复的传感器故障与通信故障；可靠场景注入数据/ACK 丢失、CRC 损坏、数据/ACK 重复和 ACK 延迟。接收会话由模拟看门狗的可信状态显式同步。它未使用网络套接字、串口、中断或真实设备。

| 指标边界 | 对账语义 |
| --- | --- |
| 采样与队列 | `sampled = sent + dropped + reset_dropped + delivery_timeouts + pending` |
| 传感器 | `attempts = sampled + sensor_errors` |
| 发送调用 | `tx_attempts` 包含全部 HAL 调用；`retransmissions` 包含每个队首次之后的调用，失败调用也计数 |
| 发送确认 | 可靠模式 `sent = acknowledged`，表示 ACK 确认出队；默认模式 `sent` 仍表示链路接受出队 |
| 接收交付 | `wire_received = receiver_unique + receiver_duplicates`，仅在演示无应用级拒绝时成立 |
| ACK 解析 | `ack_received = acknowledged + invalid_acks`；坏 CRC 在解析器层计入 `ack_rejected` |
| 未确认交付 | `acknowledged <= receiver_unique`；超时或重启时，接收端可能已接受而发送端尚未确认 |

**超时未确认不等于未送达。** 接收历史与会话只保存在内存，显式重置历史或跨进程复用启动编号可能重复交付，因此本轮不声称端到端、跨进程或故障恢复后的恰好一次语义。

RAM 可靠模式对账：`1159 = 86 + 1027 + 16 + 14 + 16`；`125 = 87 + 38`；`103 = 86 + 17`。持久配置可靠模式对账：`463 = 82 + 335 + 16 + 14 + 16`；`120 = 84 + 36`；`99 = 82 + 17`。两种场景均只对首次接受的新帧调用应用交付，重复到达经过缓存抑制。87 对 86、84 对 82 的差异表明：接收端已接受的帧可能仍未被发送端确认，不能把 14 次超时解释为对端必然没收到。

停等式发送和 100 ms 退避会限制吞吐。等待队首确认时，采样仍在继续，16 帧队列满后拒绝新样本，因此此场景出现较多队满丢弃。可靠模式还注入默认模式没有的数据/ACK 丢失、损坏和重复，两种模式不是相同故障条件下的吞吐或丢包率对照，不能据此宣称丢包改善。

持久配置可靠模式另验证三个独立进程调用：`config set` 保存 25 ms / -12500 毫摄氏度并输出 generation=2；`--store ... --reliable` 成功运行；随后 `config show` 读出相同配置、generation=3，符合演示对同值配置提交一次的语义。

## 跨进程配置与恢复

文件为两个 24 字节版本 1 记录，总长严格为 48 字节，沿用 generation、CRC 和末尾提交标记。已有文件至少须有一个有效槽；未知格式、短文件、空文件和双坏槽均拒绝打开，原字节保留。新文件采用独占创建，先初始化并同步有效默认配置（100 ms、30000 毫摄氏度）。初始化中断可能留下无效文件，后续打开会拒绝该文件，不自动覆盖。父目录不会自动创建，`.epcfg` 运行配置默认加入 Git 忽略规则。

`config set FILE PERIOD_MS THRESHOLD_MC` 先校验参数，才打开或创建文件并提交配置。`config show FILE` 不创建或写文件，输出 `period_ms`、`threshold_mc`、`generation` 和 `persistent:true`。`--store FILE --demo` 读取已有配置，持锁直至退出；为了保留协议与去重演示，它会重新提交同值配置一次并发送一次重复命令。因此演示前后配置值相同，generation 会增加一次。不同采样周期的持久化演示不能直接套用默认 RAM 指标。

上一轮以四次独立进程调用完成如下实测，所有命令成功退出；本轮相关跨进程 CLI 回归已通过：

| 调用 | 采样周期 / 阈值 | generation / 结果 |
| --- | --- | --- |
| 新文件 `config set` | 25 ms / -12500 毫摄氏度 | 2，`persistent:true` |
| `config show` | 25 ms / -12500 毫摄氏度 | 2，文件字节保持不变 |
| `--store` 演示 | 25 ms / -12500 毫摄氏度 | `persistent:true`、`accounting_ok:true` |
| 演示后 `config show` | 25 ms / -12500 毫摄氏度 | 3，同值提交一次 |

持久化演示同样使用 seed=20261023、ticks=12000，总模拟时长 17000 ms。采样尝试 479，有效采样 463，传感器错误 16；发送及解析收到 246，队满丢弃 201，重启清空 16，待发 0。两项对账为 479 = 463 + 16、463 = 246 + 201 + 16 + 0。队列峰值 16，看门狗重启 1 次，配置提交/重复命令/写入尝试为 1/1/1，遥测 CRC 拒绝为 0，字节校验摘要为 2327817637。

打开会话全程排他：Windows 使用不共享的 `CreateFileW`，Linux 使用非阻塞 `flock`，并发 EdgePulse 会话立即失败；正常关闭或进程终止后释放锁。`show` 虽不修改配置，仍使用排他读写句柄，需要相应访问权限。仅支持本地普通文件，拒绝目录以及最终路径组件的符号链接或重解析点；后端不逐级遍历父目录来检查链接。

提交只触碰非活动槽，分三阶段执行：清除提交标记后同步；写第 0..22 字节后同步；最后写提交标记后同步。系统同步分别调用 Windows `FlushFileBuffers` 或 Linux `fsync`。后端成功确认后，RAM 镜像、设备配置和命令成功/去重状态才更新。文件后端拒绝 RAM 模型的部分写入参数。

写入或同步失败后，当前后端被标记为不可继续写，必须关闭重开。错误代表“结果未确认”，不能解释为“新配置必未生效”：最后一次同步失败时，磁盘可能已经包含完整新值。`store_writes` 是已接受的写入尝试数，失败尝试也计数。CLI 参数错误退出 2；I/O、锁、格式或对账错误退出 1，存储错误不输出成功 JSON，也不回显文件路径。

文件故障测试通过仅在测试 worker 中启用的 `EP_FILE_TESTING` 探针，在提交阶段握手后终止真实独立进程，再重开并核对旧或新完整配置。27 次终止覆盖清标记同步后、23 个负载字节写后、负载同步后、提交标记写后和最后同步后，均恢复完整配置。28 个写入/同步失败点均未返回应用成功，保持 RAM 配置和命令去重状态，并拒绝在失败会话中续写；短读写补齐测试也通过。生产构建没有这些测试探针。

## 缺陷植入方法

测试工具复制源码到临时目录，逐一注入 CRC 初值错误、丢弃计数缺失、命令去重失效、看门狗阈值失效、NVM 擦错槽、错误 ACK 接受、缺失重传和重复交付。每个变体必须先以严格参数编译成功，再由真实 C 测试以非零退出码检出。编译失败、运行超时和缺失编译器均作为测试环境错误，不冒充检出。每类错误重复运行 3 次，核对退出码及标准输出/错误一致；本轮 8 类全部检出，共 24 次。

这 8 类是明确选定的代表性缺陷，不等于遍历所有可能错误。通过代码字符串锚点定位变异位置，源码相应位置变化时，工具会明确失败，要求重新审核变异。独立代码审查未发现阻断问题；窗口淘汰后的旧帧按过期拒绝，仅缓存内同序号异负载判冲突，属于已明确的有界接收语义。

## 验收边界

本轮范围为 P09 的主机 C 核心、ACK/去重软件模拟与文件配置恢复，不视为 P09 全部硬件子包完成。不带 `--store` 时配置仅在 RAM 中跨模拟重启保留，进程退出后不保留；启用文件后端可跨进程恢复配置。文件测试面向明确提交边界的真实进程终止，不等于真实断电测试，也不承诺网络文件系统、块设备扇区独立性或首次创建文件目录项的掉电持久性。实际完成的验证以本报告结果表为准。

遥测仍无落盘。可靠模式增加接收端 ACK，但没有加密认证或端到端恰好一次语义。遥测接收窗口为当前显式会话内最近 16 个接受帧，配置命令窗口仍为当前启动内最近 8 个成功编号；二者用途和生命周期不同。启动编号未跨进程持久化，接收窗口也不跨进程保存。

看门狗依靠下一次 tick 检测间隔，无法在同一线程永久卡死时自行恢复；这是模拟边界。HAL 需及时返回，当前无 RTOS 调度、线程安全或 ISR 安全保证。32 位计数和启动编号会回绕，重启进程重新使用初始启动编号。

本地未运行 Linux 或 ASan/UBSan；仓库配置相应 Linux 检查与 Windows CI，远端结果以 PR 检查为准，工作流定义本身不构成运行证据。未测板端采样精度、实时抖动、真实内存峰值、功耗或电气安全。后续有开发板时，可沿 HAL 和存储提交边界迁移，根据 Flash 擦除/编程约束适配，再开展至少 30 分钟实采、断线/拔设备/写配置掉电和栈水位验证。
