# EdgePulse C

可移植的 C 设备内核，支持有界 ACK 重传、接收去重、确定性故障模拟和主机配置持久化。

**无需开发板、现成固件或虚拟机，即可编译运行嵌入式采集链路，验证通信协议、确认丢失、有界重传、重复抑制、配置恢复和看门狗重启。**

## 快速开始

需要 C11 编译器；测试另需 Python 3.9 以上，仅使用标准库。程序和核心模块全部使用 C，无第三方运行库依赖。

Windows 环境，GCC 已加入 PATH 时：

```powershell
./scripts/build.ps1 -Mode test
./build/edgepulse.exe --demo
```

若 GCC 或 Python 不在 PATH 中，给脚本传入 `-Compiler` 和 `-Python` 的可执行文件路径。支持 MSYS2 GCC，无需虚拟机。

Linux 环境：

```sh
make test
./build/edgepulse --demo
make sanitize
```

更换随机种子并输出 JSON：

```powershell
./build/edgepulse.exe --seed 42 --ticks 12000 --json
```

启用接收确认和有界重传：

```powershell
./build/edgepulse.exe --reliable --demo
./build/edgepulse.exe --reliable --seed 42 --ticks 12000 --json
```

`--reliable` 需显式启用，可与 `--store FILE` 组合。不加该参数时沿用原演示和 JSON 字段语义。可靠模式让数据与 ACK 分别经过字节流解析器，注入丢失、CRC 损坏和重复；ACK 先进入队列，等设备 tick 返回后才交付。这是主机模拟，没有真实 UART 或网络连接。

保存配置，在另一个进程中读取，再使用该配置运行演示：

```powershell
./build/edgepulse.exe config set build/device.epcfg 25 -12500
./build/edgepulse.exe config show build/device.epcfg
./build/edgepulse.exe --store build/device.epcfg --demo --json
./build/edgepulse.exe config show build/device.epcfg
```

Linux 使用 `./build/edgepulse`，其余参数相同。`set` 可创建不存在的文件或更新已有有效文件；`show` 和 `--store` 要求文件已存在且有效。父目录必须事先存在。带空格的路径需加引号；Windows CLI 与后端支持 Unicode 路径。本地 `*.epcfg` 文件默认被 Git 忽略。

`config set FILE PERIOD_MS THRESHOLD_MC` 的周期范围为 10..60000 ms，阈值范围为 -40000..125000 毫摄氏度。`set` 与 `show` 输出包含 `period_ms`、`threshold_mc`、`generation` 和 `persistent:true` 的 JSON。`show` 不创建或写入文件。演示持有文件锁直至退出，并将加载到的同值配置通过协议重新提交一次，再发送重复命令：配置值保持不变，成功提交会让文件版本号增加一次。演示 JSON 包含生效配置及 `persistent` 状态。

`--ticks` 范围为 10..1000000，每步推进 1 ms；`--seed` 范围为 1..4294967295。场景还会注入一次 5000 ms 停顿。退出码 0 表示成功，2 表示非法参数，1 表示存储、锁、格式或对账错误；存储错误不输出成功 JSON。`--help` 查看参数。

## 设计

| 模块 | 当前实现 |
| --- | --- |
| `src/protocol.c` | CRC16-CCITT-FALSE、小端序编码、82 字节流缓冲、半包粘包解析和逐字节重同步 |
| `src/store.c` | 两个 24 字节记录、版本与 CRC 校验、最后字节提交、RAM 中断测试、版本序号回绕和可选提交回调 |
| `src/file_store.c` | 48 字节主机配置文件、排他会话、三个同步提交阶段和有效槽恢复 |
| `src/device.c` | 协作式采样、传感器与发送 HAL、16 帧 FIFO、过载对账和可选停等式 ACK 重传 |
| `src/receiver.c` | 显式设备/启动会话、16 帧去重窗口、序号顺序校验及应用接受后确认 |
| `src/main.c` | 配置命令、可选文件配置/可靠模式、确定性故障、独立数据/ACK 解析与对账 |

协议、存储、设备与接收核心不使用动态内存分配，也不依赖操作系统；主机 CLI 与文件后端可为 Windows Unicode 转换分配内存。HAL 和接收回调串行执行，要求及时返回且不可重入所属对象；当前不提供线程或中断同步。每次 tick 最多采样一次、调用一次发送 HAL，迟到的采样周期单独计数，避免集中补采。使用无符号毫秒差处理时钟回绕，相邻调用间隔必须小于 2^31 ms。

阈值控制输出为遥测中的告警标志，尚无真实执行器驱动。模拟看门狗在下一次 tick 检测到至少 5000 ms 调度间隔时重启：增加启动编号、记录队列清空数量、清除命令去重窗口并恢复配置。

### 通信协议

所有多字节字段采用小端序，最大负载 64 字节。

| 字节偏移 | 字段 |
| --- | --- |
| 0..1 | 同步头 `A5 5A` |
| 2..3 | 版本 `01`、消息类型 |
| 4..5 | 设备编号 uint16 |
| 6..9 | 启动编号 uint32 |
| 10..13 | 序号或命令编号 uint32 |
| 14..15 | 负载长度 uint16 |
| 16.. | 负载，末尾附 uint16 CRC |

CRC 覆盖版本字段至负载末尾，多项式 0x1021、初值 0xFFFF，不反射、不做末尾异或；`123456789` 的结果为 0x29B1。类型 1 遥测负载为 `时间戳:u32 + 毫摄氏度:i32 + 告警:u8`；类型 2 配置负载为 `采样周期:u32 + 阈值:i32`，要求设备编号及启动编号匹配。类型 3 为零负载的遥测 ACK，其设备、启动和序号字段回显被接受的遥测；配置命令不使用此 ACK。

解析器接受任意大小的传输片段。接收空闲或会话结束时，由调用者执行 `ep_parser_flush`，丢弃截断候选并恢复其后已完整的帧。解析器自身不管理时钟和空闲超时。CRC 用于检测误码，不提供命令身份认证。

### 配置与传输语义

- 采样周期为 10..60000 ms，阈值为 -40000..125000 毫摄氏度；核心默认值及新文件初始化值为 100 ms、30000 毫摄氏度。默认 RAM 演示会提交 10 ms、30000 毫摄氏度，`--store` 演示沿用已保存的值。
- 配置先写入成功再生效。每个启动会话缓存最近 8 个成功命令编号；同编号同参数不重复写入，同编号异参数返回冲突。窗口淘汰或重启后不再保证该编号去重。
- 队列满时丢弃新样本并计数。默认模式发送失败保留队首，发送成功即出队，只表示模拟链路接受。可靠模式保留队首，直到匹配 ACK 到达，或因超时/重启明确丢弃。两种模式都不持久化遥测。
- 不带 `--store` 时，RAM 配置槽可跨同一进程内的模拟重启保留，下一次进程启动时重新初始化为空。可选文件后端使配置跨进程保留；主机文件协议没有实现 MCU Flash 擦除、时序或磨损行为。
- 启动编号和计数器使用 uint32，会回绕；启动编号不跨进程持久化。需要全局唯一会话的场景应接入持久化启动编号或会话标识。

### ACK 重传与接收去重

在采样、发送或重启发生前调用 `ep_device_enable_reliable`；此前可以执行配置命令。重复启用或设备已活动时启用会失败且不修改状态。默认 `EP_ACK_TIMEOUT_MS=100`、`EP_MAX_RETRIES=3`：每个队首最多调用 4 次发送 HAL，包含首次发送和最多 3 次重传。每次调用都消耗预算，返回 `false` 也一样；后续调用至少间隔 100 ms。第 4 次调用后再等待 100 ms，仍未确认则出队并增加 `delivery_timeouts`，该 tick 不发送下一个队首。重传保持原帧字段和负载不变。

只有当前队首至少成功提交过一次 HAL，且 ACK 类型为 3、长度为 0、设备/启动/序号完全匹配时，才能确认出队。之后一次重传失败不会取消此前成功提交的 ACK 资格。重复、过期或不匹配的 ACK 不能弹出其他帧。看门狗重启清空重传和 ACK 状态及待发队列，保留可靠模式；ACK 输入在 `ep_device_tick` 和发送回调返回后串行交付。

接收端只接受类型 1、长度 9、告警字节为 0 或 1，且设备和启动编号匹配当前显式会话的遥测。由可信会话控制调用 `ep_receiver_begin_session` 切换启动编号，收到一帧不能自动开启新会话；切换会清空历史和序号高水位，累计指标保留。接收端缓存最近 16 个完整的已接受帧：相同缓存帧可再次 ACK，但不重复调用交付回调；同一缓存序号的负载变化属于冲突，不产生 ACK。

缓存之外的新序号必须满足无符号差值 `0 < 新序号 - 高水位 < 2^31`。允许序号跳跃和 uint32 回绕；更旧、已淘汰、相等或恰好相差半圈的序号均按过期拒绝。会话首个有效序号直接接受。只有应用交付回调成功，才推进历史/高水位并产生 ACK；失败保持该帧可重试，ACK 输出不被改写。回调返回 `false` 前若已产生副作用，重试可能重复该副作用；返回 `true` 表示应用接受，不表示数据已落盘。

可靠模式 JSON 区分以下边界：

| 字段 | 含义 |
| --- | --- |
| `tx_attempts` / `retransmissions` | 全部发送 HAL 调用 / 每个队首次调用之后的调用，均包含失败调用 |
| `sent` / `acknowledged` | 有效 ACK 确认出队数；可靠模式下两者相等 |
| `delivery_timeouts` | 等待预算用尽后出队的未确认帧数 |
| `wire_transmitted` / `wire_received` | 在线链路编码提交数 / 有效解析的遥测到达数，后者包含重复 |
| `receiver_unique` / `receiver_duplicates` | 应用接受的新遥测数 / 缓存命中的重复到达数 |
| `invalid_acks` | 已解析但不能确认当前合格队首的 ACK 数 |
| `data_lost`、`data_corrupted`、`ack_lost`、`ack_rejected` | 注入的数据丢失/损坏、ACK 丢失与 ACK 解析拒绝数 |

发送端守恒式为 `sampled = sent + dropped + reset_dropped + delivery_timeouts + pending`，以及 `attempts = sampled + sensor_errors`。有效演示中的原始到达满足 `wire_received = receiver_unique + receiver_duplicates`。ACK 丢失可能导致 `receiver_unique > acknowledged`：超时表示**交付未确认**，不等于对端没有收到。去重状态只在内存和当前会话内有效，重置会话或复用启动编号可能再次交付；协议没有认证、遥测持久日志或端到端/跨进程恰好一次保证。

停等式发送会限制吞吐：缺少 ACK 时队首持续占用发送位置，新样本仍会到来，失败 HAL 调用也消耗重试时间。本轮默认可靠场景中，1159 个样本分为确认 86、队满丢弃 1027、重启清空 16、超时未确认 14、待发 16；接收端接受 87 个唯一帧、抑制 38 次重复到达，共发生 102 次重传。87 个已接受与 86 个已确认的差异，直接体现应用接受和发送端确认的区别。可靠模式与默认模式注入的故障条件不同，不能用这些数量宣称丢包率得到改善。

### 持久配置

文件精确包含两个 24 字节的版本 1 记录，每条记录含版本序号、配置、CRC 和末尾提交字节。已有文件必须精确为 48 字节，且至少一个槽有效。未知格式、截断文件或双槽损坏会被拒绝，原字节不被改写；单槽有效时可继续恢复。新文件使用独占创建，先写入并同步有效默认记录，再提交请求的配置。初始化中断可能留下无效文件，后续打开会拒绝该文件，不会自动覆盖。

每次打开会话持有排他锁：Windows 使用不共享的 `CreateFileW`，Linux 使用非阻塞 `flock`。并发 EdgePulse 会话会立即失败，持有者关闭或进程终止后释放锁。`show` 的配置语义只读，但使用相同的排他读写句柄，仍需要相应文件访问权限。仅支持本地普通文件，拒绝目录及最终路径组件的符号链接或重解析点；后端不逐级遍历父目录来检查链接。

每次更新只修改非活动槽，顺序为：

1. 清除该槽的提交字节，并同步文件。
2. 写入含 CRC 的第 0..22 字节，并同步文件。
3. 写入末尾提交字节，并同步文件。

Windows 同步调用为 `FlushFileBuffers`，Linux 为 `fsync`。后端确认提交后，才更新 RAM 镜像、设备生效配置和成功命令历史。I/O 或同步错误表示结果未确认：最后一次同步失败时，重开仍可能读到完整新配置。失败后后端拒绝继续写入，必须关闭重开。`store_writes` 统计已接受的写入尝试，包含失败尝试，不是持久化成功次数。RAM 模型仍支持部分写入注入，文件后端仅接受完整记录操作。

进程终止测试检查明确写入/同步边界上的恢复行为；它不证明真实掉电持久性、网络文件系统行为、扇区独立性或首次创建文件时目录项的掉电持久性。

## 验证

```sh
python scripts/check_mutations.py --compiler gcc
```

标准测试入口运行 5 个 C 测试程序、14 个 CLI 测试及 14 个文件后端进程测试。协议测试逐条对账 10000 帧并处理 100000 字节异常流；存储测试覆盖 50 个 RAM 中断位置和外部提交边界；设备测试覆盖溢出、重试、传感器故障、看门狗、时钟回绕、重复与冲突命令、协议字段校验及提交失败。发送端与接收端各新增 13 组测试，覆盖 ACK 资格、调用预算、失败发送退避、重启隔离、去重、序号回绕/淘汰、显式会话和回调失败。文件测试包含 27 次提交边界真实进程终止、28 个写入/同步失败注入点，以及锁、格式和访问检查。

2026-10-25 使用 Windows GCC 13.2.0，通过 PowerShell 全套测试及新构建目录下的 Make 验证：协议 8/8、存储 10/10、既有设备测试、可靠发送端 13/13、接收端 13/13、CLI 14/14；文件测试 14 项中 13 项通过，仅跳过 POSIX FIFO。Windows 符号链接拒绝测试实际执行成功。8 类缺陷植入各重复 3 次且结果可复现，共 24 次检出；新增类型为错误 ACK 接受、缺失重传和重复交付。编译失败或超时不算成功检出。

本轮已复核不带 `--store` 或 `--reliable` 的默认 RAM 兼容基线：种子 20261023 产生 1159 个有效样本，交付 593、队满丢弃 550、重启清空 16、待发 0；另有 40 次传感器读取失败，遥测摘要仍为 3411655967。报告保留此前 25 ms / -12500 毫摄氏度配置的默认模式基线：463 个样本、交付 246、队满丢弃 201、重启清空 16、待发 0。本轮组合 `--store` 与 `--reliable` 实测 463 个样本、确认 82、接收唯一交付 84、重复到达 36；配置值不变，generation 从 2 增为 3。两个可靠模式演示均为 `accounting_ok:true`。完整指标和边界见[验收报告](docs/验收报告.md)。

Make 在 Windows MSYS2 环境中使用新的 `build/reliable-make-check` 目录，不等于 Linux 实机验证。本地未运行 Linux 或 ASan/UBSan；远端结果以本轮 PR 的 GitHub Actions 检查为准，工作流定义本身不构成运行证据。

## 迁移到开发板

把传感器和发送回调替换为 ADC/I2C/SPI/UART 驱动，使用单调时钟调用 tick；将 UART/DMA 数据送入解析器，并按明确的空闲超时调用 flush。在存储提交边界接入板端 Flash 后端，根据擦除和编程约束适配记录格式与提交顺序；主机文件后端不是板端驱动。随后在板端验证中断竞态、Flash 约束、真实看门狗、栈空间和电气故障。本项目尚不包含 MCU 启动文件、链接脚本、BSP、RTOS 或实板验收结果。
